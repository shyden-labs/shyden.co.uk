# shyden.co.uk — working agreement

- **Mobile-first, TDD, all-browser.** Base CSS is small-screen; enhance up. No horizontal scroll ≥320px; touch targets ≥44px; WCAG AA.
- **Every page ships one script, the inline theme script, and the homepage nothing else.** `src/scripts/theme.inline.js` is emitted by `BaseLayout.astro` inline and classic in `<head>`, ahead of every stylesheet, so a saved light or dark choice is on `<html>` before the first paint (#142). The homepage in all five locales and the 404 carry nothing else; `/yeetalk-calculators` and `/classroom-groups` add their own, in all five locales. `tests/e2e/theme-script.spec.ts` pins that inventory on every built page, read from a real DOM.
- **Logic is pure** (`src/lib/gloryPoints.ts`, `src/lib/grouping.ts`) and unit-tested; page scripts only wire the DOM. Change the formula or the grouping rules? Update the unit tests first.
- **Whitespace between two JSX nodes only survives while they share a line.** Assemble a sentence in the frontmatter, or write the space as `{' '}` — never rejoin the lines, because prettier re-wraps them and silently changes what the page says. Three sentences shipped broken this way. `tests/e2e/rendered-text.spec.ts` scans every built page for it.
- **`display: flex` eats the whitespace your markup authors — and no text assertion can see it.** A flex container makes its `::before` and every text node a flex _item_, and flex discards whitespace _between_ items and trims it at an item's edge. `content: '▸ '` rendered as a bare `▸`, and `Student details · <span class="state">` rendered as `·none added` — in both locales, live, for the length of a release. `textContent` still holds both spaces, so every text-based test passed; only geometry sees it. Use `gap`, never a space in `content` or between inline children. Pinned by _'a disclosure label keeps a visible gap'_ in `classroom-groups-controls.spec.ts`, which measures the pixels. This is a different failure from the JSX-newline rule above: there the formatter changes the source, here the layout mode ignores source that is already correct.
- **Scoped `<style>` cannot reach anything JavaScript creates.** Astro scopes CSS by stamping `data-astro-cid-*` onto the elements it sees at build time. Every roster row comes from `roster-ui.ts` at runtime and carries no such attribute, so a scoped rule styles the two static fields and silently misses all of them. That is what `<style is:global>` (top of `ClassroomGroupsPage.astro`) is for — the roster, the results, anything rendered by script. A spinner-reset written in the scoped block looked right in the diff and left every `#` cell in the table with its arrows.
- **A ground written as a literal carries its own ink.** A theme moves tokens, never literals. `/classroom-groups`' stale notice and gap warning painted a literal cream and took `--ink`, so when Aurora made `--ink` near-white they read 1.05:1 on `develop`, with every suite green (#332). A rule that paints its background with a literal colour paints its `color` with one too, and no rule inside it sets a token ink. That second half is not a formality: the stale sentence wore `.stale-notice p { color: var(--ink) }` whatever `.stale-notice` itself declared. `tests/unit/literal-grounds.test.ts` enforces both, reading each selector across every rule that shares it, with paper and `::backdrop` as its only exemptions. It matches by selector within one file, so each notice also has a rendered `contrastRatio` test, and that test is what caught the paragraph rule.
- **Page-level `scrollWidth` is not containment.** Content can overflow a _card_ by 34.5px and produce zero document scroll — which is exactly how the Remove button shipped hanging out of the Student details border at every laptop width. Assert against the offending element's own container (`nothing in the roster escapes its card`), not just `document.documentElement`.
- **A hand-written list of things to check will miss the one that breaks.** The no-horizontal-scroll tests opened `#cg-grouping-toggle` and `#cg-sound-toggle` — added one at a time as each section gained content — and never `#cg-io-toggle`, the only section holding a native `<input type="file">`. Its ~344px intrinsic minimum propagated up `#cg-form`'s grid (items default to `min-width: auto`) and pinned the track to 378px at every viewport: 5px of horizontal scroll at 390px, **74px at 320px**. `max-width: 100%` does not fix this — the automatic minimum reads the element's min-content size, which `max-width` does not change; an explicit `width` replaces it. The replacement test _derives_ every disclosure from the DOM, so a section added later is covered the day it appears.
- **A guard you have not watched fail is not a guard.** This repo has shipped two that asserted nothing, and both read as correct on the page. The supply-chain sub-path check (#23) was satisfied by `dependabot.yml`'s own **comment** describing the group it was meant to require — no group configured, suite green. #21 Stage 4's first replacement for the prod-smoke path list used `prod.includes(path)`, and `/glory-points` is a substring of `/id/glory-points`: the English assertion passed on the **Indonesian** path, and mutating a path to `/id/glory-pointsXX` left it green because that still contains the needle. **Every guard asserting against source text, config, or a workflow file is mutation-verified in BOTH directions before it lands** — break the thing it protects and watch it fail, then restore it and watch it pass. Strip comments before matching, so the file's documentation cannot satisfy its own guard. Prefer an exact set comparison to a substring test, and assert ORDER where order carries meaning (Dependabot stops at the first matching group). Presence is not the assertion; failure is. **And a mutation that comes back GREEN where you predicted RED has three causes, not one** (#250): the guard is weak, the mutation never reached `dist/`, or the medium made the mutation impossible. A RED is self-proving — the test failed BECAUSE of the change — so only a GREEN needs the built-output check, and that check belongs on the OBSERVED verdict rather than the predicted one, since a wrong prediction is exactly when it is needed. Rule out "never landed" by asserting the mutation's shape in the built bytes (for a REMOVAL, assert the absence WITH a liveness probe beside it, or an empty file list satisfies it for free), and rule out "weak guard" by probing the assertion's own liveness. What remains is an illegal mutation: `max-height: 40px !important` can never shrink a control, because CSS resolves a box as `max(min-height, min(max-height, height))` and a 44px `min-height` beats any smaller max-height however important it is.
- **A liveness floor is a recorded figure, checked for equality (#468).** A floor written `toBeGreaterThan(measured - 1)` is tight only on the day it is measured, because growth never fails it: `absence-liveness` read 424 an hour after it was set to `> 420`. So a guard proves it read its population with `expect(floorBreach('<id>', count)).toBeUndefined()` (`tests/floors.ts`), placed after its verdict, against the figure in `tests/floors.json`: one unit short fails, and so does one more. When a change grows a population, `npm run floors:record` raises the figure and prints every floor that moved; read each delta against your diff, because a raise smaller than the units you added is a reader that lost some, and put the lines in the commit. It never lowers a figure: a real shrink is a hand edit with the reason in the commit. CI never records. `literal-floors.test.ts` refuses a literal floor demanding two or more, however it is written (a matcher, a parameter, `n > 25` inside an `expect`, or backwards as `expect(5).toBeLessThan(n)`), unless it bounds a product value and says so. A new test file grows several floors at once, and a new file is invisible to the tracked-file guards until `git add -N`, so add it before recording.
- **A floor is half the proof; a second, number-free reading is the other half (#469).** A floor alone accepts a change that adds five units while its reader loses three, as +2. So each guard also counts its population another way and compares, per unit wherever the units can be named: in each file, the reader's count equals the same construct counted in code with its literals and comments removed (`codeWithoutLiterals` in `tests/unit/ast.ts`, so a fixture string or a comment spelling it is not one); a walk equals git's own list of the same files, both ways (`committableFiles` and `walkDisagreements` in `tests/source-files.ts`, untracked files included); a line scan equals the parse tree (`spec-scan`'s per-file `count`). **That cross-check carries no literal number**: a figure typed into it drifts exactly as a floor does. A population defined by dataflow can still be read a second way: `anchored-presence`'s text reading (`presenceOverRawText`) equals its reader in every file, and that equality is what found two units the reader counted that read nothing (#477). Where no second reading exists, the ledger says why and names what would make one.
- **No message may put a closing keyword next to an issue number — not even one you mean.** `close`/`fix`/`resolve` and their inflections, beside `#<n>`, are refused in a commit message (`.githooks/commit-msg`) and in a pull request body (`.github/workflows/pr-body.yml`), both through one home: `scripts/closing-keywords.mjs`. GitHub's parser has no model of negation, tense or intent, and it has retired an issue here **twice** — once from a sentence in capitals saying the issue must stay open, once from a body promising to retire it by hand later. There is deliberately **no exception**, because no such keyword appears in the last 300 commit bodies or 40 pull request bodies: the capability an exception would preserve has never been used, and an allowance branch nothing exercises is the vacuity #118 was filed about. Write `Refs #<n>`, and retire an issue with `gh issue close <n>` once the work is verified. Check a body before it reaches GitHub with `node scripts/closing-keywords.mjs <file> "this pull request body"`. The workflow re-runs on `edited` — a body edited after a green run is how such a sentence gets written — and `closing-keywords` is listed in develop's `required_status_checks.contexts` (#278; main's list does not carry it, read 2026-10-07). Changing either list is repository administration, and so the operator's.
- **Locale files are a review surface.** Every catalogue is typed `Catalogue`, so `npm run typecheck` (`astro check`, run in CI) fails on a missing key; it cannot read copy, so tests hold the rest. `tests/unit/i18n.test.ts` and `dead-copy.test.ts`: blank values, untranslated copy, copy no page renders. `locale-fallbacks.test.ts`: English left in zh, vi and th. `message-parity.test.ts`: every language fills the slots English fills, offers the choices it offers, and has exactly its own plural forms. `label-check.test.ts` and `verified-labels.test.ts`: a label of three words or fewer is checked against its own locale's copy that uses its English and says more, and one that disagrees, or that a namesake renders in other words, is either pinned or listed as awaiting the operator's read (#161). A label can be translated, non-blank and slot-perfect and still name the wrong thing: `Tình dục` passed every other guard here for a month. Messages are templates (#136) — English decides which entries are messages — and zh/vi/th wording is a DeepL draft until a speaker has reviewed it.
- **The e2e suite measures `dist/`**, not the dev server (`playwright.config.ts` builds and previews). Anything asserted against `astro dev` is asserting about bytes nobody receives.
- **The palette's AA floor is computed, not remembered.** `tests/unit/contrast.test.ts` scores every token pair the site paints, over the worst subset of the page atmosphere, and fails any pair under its WCAG level. Change a colour and the suite says whether it still clears; no hex value in this file is the floor.
- **Fonts self-hosted** via `@fontsource`. No external CDN / no third-party requests.
- **Six sound effects self-hosted** at `src/assets/sfx/` (shuffle, four land takes, done) — CC0 from Kenney's _Interface Sounds_ pack, mastered and shipped as our own build assets; `/classroom-groups` fetches them from our own origin only, same as the fonts above. Synthesis in `src/lib/sfx.ts` is the fallback when a sample is not ready or a browser cannot decode AAC. Licence and provenance: `src/assets/sfx/CREDITS.md`.
- **Tests:** `npm run test:unit` (Vitest; starts no process, #630), `npm run test:integration` (Vitest over `tests/integration/`: every test that starts a process, one measured limit on the script itself, run in CI right after the unit step), `npm run test:e2e` (Playwright, 6 projects — five browsers plus `content`), `npm test` (all three), and `npm run test:sanity` (the dev and prod sanity suites against this tree's own build; see **Releasing**).
- **CI runs the e2e suite as eight shards, and `build-and-test` only stands for them (#163).** `ci.yml`'s `checks` job (labels, format, build, typecheck, unit) and its `e2e` matrix (`--shard=i/N`, with N the matrix's own size, `fail-fast: false`) run in parallel. `build-and-test` is the context branch protection and `scripts/deploy-gate.mjs` read for the suite (beside `visual`, and `closing-keywords` on `develop`), so its success must still mean the whole suite ran. It needs `image`, `scope`, `checks`, the `e2e` shards, `sanity-on-build` and `functions`, runs `always()`, and fails unless every job it needs **succeeded** and the shards' own accounts add up to the unsharded `playwright test --list` total (`scripts/e2e-shards.mjs`, fed by `scripts/test-e2e.mjs` through `E2E_ACCOUNT_DIR`). A skipped required check is reported to branch protection as passing, which is why the aggregate can never be skipped and why `skipped` is refused like `failure` — with one exception: a pull request `scope` judged docs-only (`scripts/docs-only.mjs`, #582) skips exactly the shards, `sanity-on-build` and `functions`, and passes only when those, and nothing else, were skipped. A job added to `ci.yml` must be required by name (administration, and `REQUIRED_CHECKS` in the gate) or needed by `build-and-test`; `pipeline-wiring.test.ts` derives that rule rather than listing jobs. Before the split, a pull request waited 25.7 to 39.3 minutes (median 36.9, the last eight green runs) against a 45-minute budget.
- **Dependencies stay few; a new npm package is an operator decision.** The tree is deliberately small, and the answer to "add a library?" has been no wherever the platform already does the job: git's `core.hooksPath` instead of husky, hand-written SVG avatars instead of a library. The development tools declared beyond the site's own are `@astrojs/check` and `typescript` (#115, the type checker), `wrangler` (#97, exact-pinned for the deploys and the `functions` tests; it brings `workerd`), and `yaml` (dev, operator decision 2026-09-13, #157), declared so `tests/workflow-jobs.ts` can PARSE workflow files — what a job needs, and what its condition says once YAML has removed comments and unfolded blocks, is a structural question comment-stripped text cannot answer. It is pinned to the version vite already brought into the tree.
- **The visual suite is opt-in, and both sides run the same pinned image.** **Both `npm run test:visual` and `npm run test:visual:update` run inside `mcr.microsoft.com/playwright:v<installed>-noble`**, the same image `ci.yml`'s `visual` job uses — never on your machine. A local run would find no `-linux` baselines, write `-darwin` ones, and report a confident pass over a comparison it never made; that failure is silent and leaves files CI will never open. The project itself is declared only under `VISUAL=1` (the script sets it), so the ordinary e2e run keeps exactly the tests it had, and a wrong env var cannot fake a pass: `--project=visual` against a config that does not declare it is a hard Playwright error, not an empty green run. Baselines change ONE way: `npm run test:visual:update`. **The container is pinned to `--platform linux/amd64`, the architecture CI compares on** — measured on run 35657436585, all ten baselines captured on the operator's arm64 Mac differ from an `x86_64` render on **25-48% of their pixels** at zero tolerance, and `threshold: 0.1` hid every bit of it, so the tolerance was buying a whole architecture's worth of text rasterisation rather than the margin it was set for (#224; the emulation cost on Apple Silicon was put to the operator with that measurement and accepted). **And a baseline captured to prove a change invisible is re-captured once that change lands** — otherwise the committed file describes the tree before the change and quietly stops guarding the thing it was written for, which is how `classroom-groups-roster-mobile-linux.png` came to predate the CSS it covers. **A baseline captured on your laptop is not the one CI reads** — Playwright writes the platform into the filename, so a macOS capture is invisible to a Linux runner, and even where it were read, the two ship different font packages and rasterise text differently. CI never passes `--update-snapshots`, because a run that can rewrite the baseline it checks against asserts nothing; a changed baseline arrives as a reviewable diff in a PR. Determinism is engineered rather than patched in after the first flake: animations and caret are handled in `expect.toHaveScreenshot` so no call site can forget them, `document.fonts.ready` is awaited, `scale: 'css'` pins the device-pixel ratio, and no page reads the clock (`no-dated-render.test.ts`), so nothing dated can reach a baseline: the footer's copyright year needed a mask until #370 removed the line with the dissolved company. **A full-page capture holds every sticky element in normal flow** (`holdStickyInFlow`, #311). Chromium's full-page capture resizes the view to the whole page and back, and about one run in 150 on the runner the docked action bar came out of that resize with its label one pixel up-left, which a trace showed happening inside the capture itself. The elements are found by computed style, not named, and the bar's docked look is its own viewport-only picture, since a viewport capture never resizes. Moving an element on or off its own compositor layer changes how its text is anti-aliased even where the geometry is identical, which is why every baseline's header changed with this. The whole wiring is pinned by `browser-matrix.test.ts` and `pipeline-wiring.test.ts` — including that the five engines must IGNORE `visual.spec.ts`, since without that the same 8 tests are claimed by all five and demand five sets of baselines.
- **Branching: work integrates on `develop`, `main` describes what is live.** `develop` is the default branch. Feature branches PR into it; `build-and-test`, `visual` and `closing-keywords` are required. A promotion PR `develop → main` is how anything reaches production, and branch protection there requires `build-and-test` + `visual` + **`dev-verified`** (both lists read 2026-10-07). Opening that promotion PR is a release action, not a routine step — see **Releasing** below.
- **Releasing: dev is the gate, prod follows the merge.** Every push to `develop` fires `deploy-dev.yml`: it proves the merged tree is the tree that passed on its PR (`scripts/deploy-gate.mjs`, so the suite is not run twice; a dispatched branch runs it instead, by calling `ci.yml` itself rather than a copy of its steps), deploys to `dev.shyden.co.uk`, **verifies the deployed site** (`tests/dev/dev-sanity.spec.ts` via `playwright.dev.config.ts`), then posts a **`dev-verified`** commit status on that SHA. **Merge into `develop` with a merge commit, never a squash:** the gate proves the merge's tree equals its second parent's, which a squash does not have, so it refuses the deploy. **Confirm a release by reading `dev-verified` off the COMMIT and each job by name** — a run whose verify job was skipped still concludes `success` (#157). Because a status is bound to a commit and a promotion PR's head _is_ develop's head, the status main's protection wants is already on the right commit — no copying step. Merge, and `deploy-prod.yml` fires on the push, waits at the approval-gated `prod` environment, deploys, smokes every page in all five languages, **then verifies production in a real browser** (`tests/prod/prod-sanity.spec.ts` via `playwright.prod.config.ts`) before posting `prod-verified`. `release-tag.yml` tags and releases on the same push.
  **A pull request runs both of those suites first, against its own build (#335).** `ci.yml`'s `sanity-on-build` job runs `npm run test:sanity`: with `SANITY_ON_BUILD=1`, `playwright.dev.config.ts` and `playwright.prod.config.ts` each build this tree and preview it (`tests/sanity-on-build.ts`, the dev build carrying the dev ShyTalk URL as `deploy-dev.yml`'s does), and `build-and-test` needs the job. Before this, a fact kept in `tests/dev` or `tests/prod` could only go stale in front of a deploy: #330 changed a badge count, went green on every check, and failed the first dev deploy after the merge. The tests only the deployed site can answer carry `tag: '@deployed-only'` with a `deployed-only` annotation giving the reason, written where the test is, and run only after a deploy: today they are dev-sanity's _robots.txt disallows all crawling_ and _an unauthenticated request is challenged with 401_, both answered by `functions/_middleware.js`, and the report endpoint's tests (dev-sanity's _the report endpoint is bound to its migrated database_ and _a real report from the Vietnamese homepage reaches #report-sent_, prod-sanity's _the report endpoint is bound to its migrated database_), which need its D1 binding: Pages Functions a preview of `dist/` never runs. `tests/integration/sanity-on-build.test.ts` refuses the tag without a reason, and a spec file that contributes no test to the pull request's run.
  **The release protocol is the operator's, and steps 4-6 are not automated.** In order: (1) everything to be released is on `develop`; (2) `develop` deploys to dev; (3) the automated suite runs **against the deployed dev site**, and if it is not green nothing proceeds; (4) an interactive evidence page is produced for the operator; (5) the operator performs an interactive manual test; (6) **the operator, and only the operator, triggers the release to prod.** Steps 1-3 are enforced by the workflows and by branch protection, and the sections below describe how. Steps 4-6 are not enforced, deliberately: they are held by process, backed by the `prod` environment's required reviewer. The consequence to internalise is that a promotion PR `develop → main` **is a release action, not a follow-up to a green dev deploy** — do not open or merge one because `dev-verified` went green. It is opened when the operator says the manual test has passed. The `prod` environment carries `required_reviewers`, which is the mechanical stop standing behind the whole protocol; that `deploy-prod.yml` declares `environment: name: prod` is pinned by _'prod is behind the approval-gated environment'_ in `pipeline-wiring.test.ts`, so the gate cannot be deleted quietly.
  `deploy-dev.yml` keeps `workflow_dispatch` for putting an arbitrary branch on dev, but the status step is guarded by `github.ref_name == 'develop'`. Without that guard a dispatched feature branch could earn `dev-verified` and open a PR straight into `main`, skipping the integration the model exists to force. Dispatch was originally the _only_ trigger for a real reason — one shared dev environment, many PR branches, last push wins — which an integration branch removes by construction rather than by discipline.
  **Production was verified by `curl` until it wasn't enough.** Status codes and grepping fetched HTML is a text assertion, and this repo shipped a bug for an entire release that no text assertion can see (see the `display: flex` note above). It also cannot tell whether the stylesheet loaded, whether the calculators' script ran, or whether a page scrolls sideways at 320px. The smoke stays for page inventory; the browser run asserts what only rendering can. If `curl` could already prove it, it does not belong in `tests/prod/`.
  The previous pipeline (`release.yml`, deleted) deployed to prod **before** the merge and made production the gate: a mistake first became real in front of teachers, and `main` briefly did not describe what was live. Branch protection on `main` requires `build-and-test` + **`dev-verified`**. `tests/unit/pipeline-wiring.test.ts` holds the new shape up — it exists because the dev sanity suite and its config were both written and then referenced by **nothing** in CI, so "deployed to dev" meant only that `wrangler` had not errored.
- **Automation identity: agents act as `shyden-agent[bot]`, and whatever it cannot do is the operator's.** Since #245, an agent session on the operator's machine reaches GitHub as the `shyden-agent` GitHub App, installed on this repository only, instead of as the operator. `git` authenticates through a local credential helper and `gh` through a local router; both live outside this repo, in the operator's `~/.claude/scripts/github-app/`, and `SHYDEN_GH_ROUTE_TRACE=1` prints which identity each `gh` call took. The operator's own terminal is unchanged, and a commit keeps the checkout's configured author: the App is who _pushed_ it, not who wrote it. The App can push branches, open, comment on and merge PRs, edit issues and the project board, dispatch and re-run workflows, change workflow files, and draft repository security advisories. It has **no** `deployments` permission, so it cannot approve the `prod` environment: measured, its approval of a waiting run returned HTTP 403 while the operator's went through (#245, AC3). Administration, environments, secrets and commit statuses are _read-only_ to it, so it cannot change branch protection or an environment's reviewers, write a secret, or post a commit status such as `dev-verified`. Anything that needs one of those is the operator's to do: an agent that finds itself needing it stops and asks, and never reaches for the operator's login instead.
- **Real-device gauntlet:** `npm run test:devices` builds once and runs the emulated suite, real Android Chrome (over CDP) and real iOS Safari (over WebDriver) concurrently against that one build. It does **not** run in CI — CI has no phones, so this is a local, pre-release gate only. It does **not** cover Brave or Firefox on Android — neither exposes a way to drive them at all. And it proves exactly **one** iOS engine: every iOS browser is WKWebView, so "every iOS browser" here means one engine wearing different shells, not real cross-engine coverage. A live dashboard (`http://localhost:4322`, or `npm run dashboard` on its own) prints its URL at the start of the run and shows all three groups — progress, live pass/fail/skip counts, the test currently running, and the iOS interaction-mode banner — updating as the run happens; it is a read-only observer, never a way to run tests. For interactive work on a **single** config instead of the full gauntlet, use `npx playwright test --ui`, a different tool the dashboard does not replace.
