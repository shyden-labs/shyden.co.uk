# #335 — a pull request runs the deployed-site suites against its own build

Branch `335-sanity-on-build`, from `develop` at `bd2b7cde69994bbe273dc9e552247abe79a1f7c9` (#338 merged as PR #340).

## Why

`tests/dev` and `tests/prod` run only after a deploy. #330 changed a count that `dev-sanity.spec.ts` kept its own copy of, went green on all 13 checks, and failed the first dev deploy after the merge (run 35948503612). #338 is the same class in `tests/prod`. Both suites already take their base URL from the environment, and against a local production build every test passes except those that need something `dist/` does not contain.

## Measured before planning

- `playwright.config.ts` builds and previews through its own `webServer` (`npm run build && npm run preview`). The sanity configs have no `webServer`.
- Playwright spreads `webServer.env` over `process.env` (`node_modules/playwright/lib/runner/index.js:872-875`), so a config can ADD `PUBLIC_SHYTALK_URL` for its build but cannot remove one inherited from the environment.
- A dev-URL build, served locally: 26 passed, 2 failed (memory `a-local-dev-suite-cannot-pass-the-function-tests`). The two are _robots.txt disallows all crawling on the dev site_ and _an unauthenticated request is challenged with 401_. Both are answered by `functions/_middleware.js`, a Cloudflare Pages Function that `astro preview` never runs.
- A plain build against prod-sanity: 21 passed (#338's green run). No production-only test exists today.
- `dev-sanity.spec.ts:16`'s `BASE` reads `WEB_BASE_URL` directly and is used only by the 401 test (line 115), one of the two deployed-only tests.
- `ci.yml` triggers on `pull_request` only. `build-and-test` needs `[checks, e2e]`, and `scripts/e2e-shards.mjs`'s `needsFindings` judges every job it is given, so a new need needs no change there.
- Both sanity configs declare one project, chromium.
- `npm run preview` is `ASTRO_PREVIEW_BACKGROUND=1 astro preview`. That variable is the marker Astro gives its own background child (`node_modules/astro/dist/cli/preview/index.js:45`, `cli/server.js:140`), so setting it switches the agent auto-backgrounding OFF, and the server stays in the foreground where a `webServer` owns it. Astro still records it in `.astro/preview.json` (`cli/preview/index.js:137`), and a lock left behind by one run is how a second preview comes to start nothing (memory `a-second-astro-preview-starts-nothing`; CLAUDE.md's container note clears it with `rm -f .astro/preview.json`).

## Design

1. **One switch, `SANITY_ON_BUILD=1`, read in one home: `tests/sanity-on-build.ts`.** It exports `onBuild(port, buildEnv)`. When the switch is on, that returns the config fragment that makes a sanity config measure its own build: a `webServer` running `rm -f .astro/preview.json && npm run build && npm run preview -- --port <port>` (the `rm` because the dev and prod runs start previews one after the other, and the first leaves its lock), with `env: buildEnv`, `url` on `localhost` (preview binds `localhost` only), and `reuseExistingServer: false` so a stale server fails loudly. The build is the pull request's own tree built with `npm run build`, the command the e2e suite's `webServer` uses. The dev run's build differs only by `PUBLIC_SHYTALK_URL`, exactly as `deploy-dev.yml`'s build does. That is AC1's "same `dist/` the e2e suite measures": a production build of this tree, never the dev server. It returns `{ webServer, grepInvert: /@deployed-only/, baseURL: 'http://localhost:<port>' }`, or `undefined` when the switch is off, so a deploy's run is unchanged. A config does NOT spread it whole: `use` is nested, and a top-level spread carrying `use` would replace the config's `use` and drop `colorScheme` and `httpCredentials`. Each config takes `webServer` and `grepInvert` at the top level, and writes `baseURL: build?.baseURL ?? process.env.WEB_BASE_URL ?? '<deployed host>'` inside its own `use`. The dev config passes `{ PUBLIC_SHYTALK_URL: 'https://dev.shytalk.shyden.co.uk' }` (the value `deploy-dev.yml:128` sets) on port 4398. The prod config passes `{}` on port 4399, and **throws** when the switch is on and `PUBLIC_SHYTALK_URL` is set. It cannot unset the variable, and a production-sanity run over a dev-URL build would test the wrong site.
2. **Deployed-only is a tag with a reason, where the test is written.** `tests/sanity-on-build.ts` also exports `deployedOnly(reason)`, which returns `{ tag: '@deployed-only', annotation: { type: 'deployed-only', description: reason } }`. The two function tests take it as their details argument. The tag is what `grepInvert` filters, and the annotation carries the reason into every report.
3. **`npm run test:sanity`** runs `SANITY_ON_BUILD=1 playwright test -c playwright.dev.config.ts && SANITY_ON_BUILD=1 playwright test -c playwright.prod.config.ts`, with the same inline-env form `preview` already uses. It works locally with no preview running, no credentials and no `PUBLIC_SHYTALK_URL`.
4. **A CI job, `sanity-on-build`**, in `ci.yml`, with `timeout-minutes: 15` like every job there: checkout, setup-node, `npm ci`, `npx playwright install --with-deps chromium`, then `npm run test:sanity`. It uses the same SHA-pinned actions as `e2e`, and on failure it uploads its traces like the shards do. `build-and-test`'s `needs` becomes `[checks, e2e, sanity-on-build]`, so the one required context stands for it (AC4) and no branch-protection change is needed.
5. **The guard (AC2), `tests/unit/sanity-on-build.test.ts`.** For each sanity config, it takes the spec files under the config's `testDir`, derived with `specFilesUnder`. It runs `playwright test --list --reporter=json` with `SANITY_ON_BUILD=1`, and asserts every spec file contributes at least one test. A second listing without the switch asserts every test carrying `@deployed-only` has a `deployed-only` annotation with a non-empty reason, and that the on-build listing contains none of them. Both of those are absences, so each runs through `searched(findings, { of: taggedTests, what })`: a tag misspelled everywhere would leave no tagged test, and without the population both would pass having measured nothing. `--list` must not start the `webServer`, and Task 1 measures that before anything depends on it.
6. **`CLAUDE.md`** (AC6): the Releasing section says a pull request runs `tests/dev` and `tests/prod` against its own build (`sanity-on-build`), with `@deployed-only` tests left to the deploy's run, and says which those are.

## Implementation notes (2026-09-25, 14:18-14:29Z): where the build departed from the plan, and why

- **The `rm -f .astro/preview.json` is gone.** Task 3's control ran `test:sanity` without it, with a lock left behind, and passed (27 + 21). The plan predicted RED and was wrong: `checkExistingServer` (`astro/dist/core/dev/lockfile.js:122`) removes a lock whose process is dead. The only lock that blocks a preview names a live one, and there an `rm` would delete another preview's lock. Per Task 3's rule, the `rm` was deleted.
- **`deployedOnly()` is gone; the details are literals.** `playwright-declarations.test.ts` refused a call as details it cannot read, because the tag guards read the parse tree. The meta-guard was right, so the code changed. The tag and its reason are written inline, and the unit guard's annotation check is what requires the reason.
- **The `@deployed-only` population is pooled across both configs.** Prod has no deployed-only test, so a per-config `searched` would throw on an empty population that is correct.
- **An empty on-build selection is read as a listing of no tests.** G1 first went red for the wrong reason: each testDir holds one spec file, so tagging all of a file's tests empties the selection, Playwright exits 1 with `No tests found`, and the coverage assertion never ran. Now it runs and names the file. G1b (a second, fully tagged spec file beside a healthy one) proves the non-empty branch.
- **The guard also asserts the switch itself** (`webServer` absent on a deploy's listing, present and building on the on-build one), and the coverage test anchors on it first. Without the anchor, coverage read against stubs would have passed.
